# 평가와 실험 설계

- 버전: v0.2, 2026-10-08
- 상태: 실행 전 실험 계획. 아래 수치·예시는 실측 결과가 아님.
- 연결 문서: [개발 계획](PLAN.md), [아이디어 목록](IDEAS.md)

## 평가 질문

**Decisions를 사용해 실행 정책을 선택하면, 같은 작업의 검증된 완료 품질을 유지하면서 총비용이나 완료 시간을 개선할 수 있는가?**

정책은 모델·effort와 검증·허용된 복구 경로의 조합이다. 분류 정확도와 높은 confidence는 보조 신호다. 평가 대상을 "난이도 맞히기"로 축소하지 않는다.

첫 파일럿은 품질을 채택의 선행 조건으로 두고 **검증된 완료당 총비용**을 주된 효율 지표로 사용한다. 시간은 보조 지표다. 시간 중심의 확증 실험을 하려면 결과를 보기 전에 그 지표를 따로 지정한다.

## 공통 프로토콜

1. 과제, 시작 커밋·파일 내용, 완료 기준, 실행 제약, 전체 시간·비용 예산을 고정한다.
2. 개발 과제와 잠금 평가 과제를 저장소·과제군 단위로 분리한다. 같은 버그의 변형을 양쪽에 넣지 않는다.
3. 비교할 프로필·정책·질문·검증기 버전과 주 지표를 실행 전에 고정한다.
4. 지원하는 동일 과제에서 짝지은 실행을 하고 순서를 무작위화한다. 초기 상태를 복원하고 cache 상태를 기록한다.
5. 분류·탐색·모든 시도·통합·검증을 계측한다. 실패·취소·설정 불일치도 포함한다.
6. 반복 실행의 변동성을 기록하되 반복을 새로운 독립 과제로 세지 않는다. 신뢰구간은 과제·저장소군의 의존성을 반영한다.
7. 잠금 평가를 보고 정책을 고치면 기존 결과는 탐색 결과로 남기고 새로운 확증 자료를 사용한다.

초기 데이터 제안은 개발 30개, 평가 30개이며 중요한 비교는 최소 3회 반복한다. 규모와 실행 예산은 실제 호출 전에 확정한다. 작은 파일럿으로 좁은 비열등성 한계를 입증했다고 주장하지 않는다.

실행 가능한 완전 명세 과제와, 올바른 동작이 `needs_input`·접근 거부·무실행인 처리 과제를 구분한다. 후자는 적절한 처리 비율로 평가하고, 질문만 한 상태를 코딩 작업의 검증된 완료로 세지 않는다. 부적절하게 실행한 결과를 빠른 성공으로 보상하지 않는다.

## 필수 비교 기준

| 코드 | 비교 방식 | 분리해 확인하는 효과 |
| --- | --- | --- |
| B1 | 고정 efficient | 낮은 자원만 쓰는 기준 |
| B2 | 고정 general | 기본 단일 실행 기준 |
| B3 | 고정 deep | 높은 자원만 쓰는 기준 |
| B4 | 단순 결정적 규칙 | API 분류의 추가 가치 |
| B5 | 프로필 사용 비율을 맞춘 무작위 배정 | 같은 비율에서 적절한 과제에 배정하는 효과 |
| B6 | 저비용 우선 → 검증 → 허용된 복구 | 사전 선택과 실행 후 검증·추가 실행의 차이 |
| B7 | Decisions의 루트 라우팅 | 루트 선택 정책의 전체 효과 |
| B8 | 같은 분해, 고정 worker 프로필 | 위임된 작업의 기본 배정 |
| B9 | 같은 분해, worker별 Decisions 라우팅 | 하위 작업별 선택의 추가 효과 |

B1–B7은 자식 생성을 끈다. B8·B9는 같은 부모 설정·저장된 작업 분해·worker 수·검증·예산을 사용한다. 지원하지 않는 프로필을 실행해 보거나 제약을 완화하지 않는다. 공통 지원 과제군을 사전 정의하고, 전체 사용성 보고에는 지원 불가 비율도 남긴다.

B5는 호환성과 작업군 안에서 비율을 맞춘다. 실행 결과를 보고 배정을 최적화하지 않는다. 사후에 관측한 B7의 비율로 맞춘 비교라면 사후 통제임을 표시한다. 호출 비율이 같아도 토큰·복구 비용은 다를 수 있으므로 실제 총비용을 측정한다.

B6의 복구 대상은 첫 검증에서 거절된 작업이다. 복구 비용·성공률을 모든 과제의 평균으로 대신하지 않는다. 본 시스템의 단순한 B6를 특정 논문의 완전 재현이라고 부르지 않는다.

실행 전 예상 호출 수와 예산을 계산하고 작은 개발 실험부터 단계적으로 진행한다. 예산 때문에 비교하지 못한 방식은 미실행으로 남기고 결론의 범위를 제한한다. 모든 비교를 즉시 실행한다는 계획이 아니다.

## 측정 정의

| 항목 | 정의 |
| --- | --- |
| 검증된 완료율 | 사전 완료 기준을 충족하고 수락된 과제 수 / 실행 대상 과제 수 |
| 완료당 비용 | 전체 시도·분류·검증 비용 합 / 검증된 완료 수; 분모 0은 정의 불가 |
| 실제 종료 시간 | 시작부터 성공·실패·취소 등 실제 종료까지의 벽시계 시간 |
| 검증된 완료 시간 | 시작부터 검증 완료까지의 시간; 미완료는 별도 상태 |
| 제한 완료시간 | 기한 D 안에 완료하면 그 시간, 아니면 D; 실제 관측 시간과 구분 |
| 잘못된 통과 | 독립 판정에서 부정확한 결과를 운영 검증기가 통과시킨 사례 |
| 잘못된 탈락 | 독립 판정에서 적절한 결과를 운영 검증기가 탈락시킨 사례 |
| 운영 상태 | 생략·fallback·refusal·미관측 설정·중복 방지·취소·예산 초과 |

총비용은 원시 사용량과 당시 단가·추정 가정을 함께 남긴다. API 청구액, 구독 사용량, 로컬 자원 비용은 같은 금액처럼 합치지 않는다. 직접 금액을 알 수 없는 항목은 환산 가정과 불확실성을 표시한다. 아직 정산되지 않은 사용량을 0으로 처리하지 않는다.

반복이 있는 과제에서는 정책별 총비용과 완료 건수를 같은 방식으로 집계한다. `E[비용] / P(완료)`는 해당 평가 모집단에서의 완료당 비용 표현이며, 한 요청의 성공 확률을 Decisions가 제공한다는 뜻이 아니다.

## E01

### 후보 실행 결과와 개선 여지

**가설:** 작업에 따라 유리한 프로필이 달라 실제 라우팅으로 활용할 여지가 있다.

- 개발 과제의 일부를 지원하는 후보 프로필에서 각각 실행한다. 초기 설정 예시는 10개 과제·최대 3개 프로필이며 실행 예산 안에서 확정한다.
- 다음 항목을 기록한다: `task_id`, `snapshot_hash`, `profile_id`, `model`, `effort`, `attempt_id`, `settings_evidence`, `verification`, `cost`, `wall_time`, `failure_reason`.
- 실행하지 않은 조합은 `unknown`, 지원 불가는 `unsupported`, 충분히 검증할 수 없는 결과는 `inconclusive`로 남긴다.
- 같은 과제·반복에서 관측한 성공 결과 중 가장 저렴한 것을 고르는 사후 기준을 계산한다. 성공 결과가 하나도 없으면 성공을 만들어 넣지 않는다.
- 사후 기준은 후보 결과를 모두 알고 고른 참고값이다. 제한된 후보·반복에서의 낙관적 개선 여지를 보여주며 실제로 배포할 수 있는 라우터나 보편적 상한은 아니다.

**진행 조건:** 비싼 후보만 늘려도 해결되지 않는 과제와 프로필 차이로 개선되는 과제가 구분돼야 한다. 관측된 개선 여지도 작으면 라우터 복잡도를 늘리기 전에 범위를 조정한다. 반복 중 우연히 성공한 한 결과만으로 최선 프로필을 확정하지 않는다.

## E02

### 라우팅·모델·effort의 효과

**가설:** B7이 기본 실행과 단순 배정·cascade보다 유리하다.

- B1–B7에서 같은 과제·시작 상태·최종 검증·전체 예산을 사용한다.
- 모델 고정/effort 선택, effort 고정/모델 선택, 둘 다 선택을 나누어 본다. 모델마다 동일한 effort 라벨이 같은 계산량이라고 가정하지 않는다.
- B4·B5·B6보다 나아지는지 보고, 기본 프로필보다 좋아졌다는 비교만으로 선택 정확성의 가치를 결론내리지 않는다.
- 주 지표는 완료당 총비용이고, 완료율·회귀·제한 완료시간과 실제 지연 분포를 함께 보고한다.

**진행 조건:** PLAN의 탐색 목표인 비용 20% 개선 여부를 보되 품질 회귀와 불확실성이 선행 조건이다. 작은 평가 집합으로 5%p 비열등성이 입증됐다고 하지 않는다. 사전 정의한 작업군에서 악화하면 해당 군의 자동 배정을 보류한다.

### 계산 예시

아래 숫자는 측정값이 아닌 설명용 가정이다. 첫 실행 비용 $0.02, 각 검증 $0.005, 복구 실행 $0.10이고 검증이 정확하며 복구가 항상 성공한다고 가정한다. 맥락 전달·라우팅 비용은 이 예시에서만 0으로 둔다.

`저비용 우선 기대 비용 = 0.025 + 첫 실패 확률 × 0.105`

| 첫 실행 성공률 가정 | 저비용 우선 기대 비용 | 직접 복구 프로필로 실행 |
| --- | --- | --- |
| 70% | $0.0565 | $0.105 |
| 10% | $0.1195 | $0.105 |

처음 호출이 싸다는 사실만으로 전체 경로가 싸다고 결론낼 수 없다. 실제 실험에서는 조건부 복구 성능, 검증기의 오판, 분류·맥락 전달 비용도 포함한다.

## E03

### 검증기의 판정과 복구 경로

**가설:** 저비용 우선 정책의 이득은 검증기가 잘못된 작업을 발견하는 능력에 의존한다.

- 운영 검증과 평가용 독립 판정을 구분한다. 작업 시작 전 완료 기준과 필요한 검사를 고정한다.
- 겉보기 형식만 맞는 오류 결과, 얕은 테스트만 통과하는 결과, 정상 결과, 환경 때문에 검사할 수 없는 결과를 포함한다.
- `passed`, `failed`, `inconclusive`, `blocked`를 확인하고 잘못된 통과·탈락의 건수와 분모를 보고한다.
- 첫 실패 작업에 전달할 실패 검사·diff·미해결 제약을 고정하고, 같은 프로필의 복구와 다른 프로필의 복구를 비교할 수 있다.
- verifier 오류 주입을 한다면 인위적 민감도 시험으로 표시한다. 주입한 오류율을 실제 오류율처럼 보고하지 않는다.

**진행 조건:** 중요한 검증 누락이나 기준 약화로 통과하는 사례가 남으면 해당 과제군에 저비용 우선 자동 완료를 적용하지 않는다. 테스트 변경이 정당한 경우에도 별도 검토와 고정 평가 기준을 유지한다.

## E04

### 맥락 수집·분류 생략·캐시

**가설:** 선택이 확정된 요청은 생략하고, 불확실한 요청에만 필요한 맥락을 수집하면 전체 효율이 개선된다.

- 완전 고정 설정, 모델만 고정된 설정, 호환 후보 하나, 짧지만 어려운 요청, 긴 기계적 요청을 포함한다.
- 기존 정보만 사용, 단계별 수집, 넓은 선행 수집을 비교한다. 독립 질문을 한 번에 보내는 것과 불필요하게 여러 요청으로 나누는 차이도 측정 후보로 둔다.
- 필요한 사실이 없는 경우, 사용자의 핵심 결정이 없는 경우, 라우터만 불확실한 경우의 다음 상태를 확인한다.
- 캐시를 추가하면 과제·관련 파일·미커밋 diff·질문·모델·프로필·제약 버전 변경마다 무효화되는지 검사한다.

**진행 조건:** 명시 설정·단일 후보의 분류 호출은 0회이며 필수 제약 검사는 유지돼야 한다. 추가 맥락의 가치가 최종 완료 품질·비용으로 확인되지 않으면 수집 범위를 줄인다.

## E05

### 실행기·hook·취소·예산의 장애 시험

**가설:** 실행 상태와 설정의 증거를 구분하면 중복 작업·오판·잘못된 정산을 예방할 수 있다.

| 주입 사례 | 기대 동작 |
| --- | --- |
| 지원하지 않는 모델·effort | 실행 전 명확한 오류 |
| custom-agent의 설정 덮어쓰기 | 요청과 런타임 보고 불일치 기록 |
| hook 미신뢰·누락·잘못된 출력·timeout | 모드별 동작 확인. 이미 시작한 자식과 대체 worker의 중복 실행 금지 |
| 시작 직후 응답 유실 | outcome_unknown, 프로세스·세션 대조 전 재시작 금지 |
| 산출물 생성 후 controller 중단 | 산출물 버전·검증 상태를 복구하고 중복 수락 방지 |
| 취소 요청·자식 종료 지연 | cancelling과 cancelled를 구분, 새 호출 중지 |
| 동일 사용량·종료 이벤트 중복 | 이중 정산·중복 결과 수락 없음 |
| 두 worker의 동시 예약 | 예약 원자성, 완료용 예산 보존 |
| 모델만 보고되고 effort 미보고 | 부분 관측으로 표시 |
| 데이터 전송 금지·fixture·기본 doctor | 원격 추론 호출 0회 |

먼저 mock 실행기로 상태 계약을 검사하고, 지원 여부가 확인된 live 런타임에서는 최소 사례만 검증한다. hook 동작 시험을 위해 trust·sandbox·권한을 우회하지 않는다. 관측이 없으면 불가능한 강한 보장을 문서에 추가하지 않는다.

**진행 조건:** 시작·취소·복구가 지원 범위에서 재현되고, 미확인 실행이 중복 작업을 만들지 않아야 한다. native 모드가 필요한 제약을 보장하지 못하면 시작 전 외부 worker 모드로 제한한다.

## E06

### 하위 작업별 배정과 전체 완료

**가설:** 같은 작업 분해에서 worker별 설정 선택이 고정 배정보다 유리하다.

- B8·B9에 저장된 동일 분해·부모 설정·worker 수·의존성·완료 기준을 제공한다. 종속 작업은 필요한 선행 증거가 생긴 뒤 분류한다.
- 각 비교는 깨끗한 시작 상태에서 실행한다. 상위 작업이 생성한 산출물 차이는 전체 워크플로 결과의 일부로 기록한다.
- 순수한 leaf 라우팅 효과를 추가로 분리할 때는 공통 선행 산출물을 고정한 별도 실험을 사용한다.
- parent 계획·통합, worker, 분류, 전달, 최종 검증의 비용과 지연을 분리한다.
- 파일·포트·DB·quota 충돌과 완료 예산 확보를 점검한다. 준비·대기 비용이 큰 경우 순차 실행과 비교한다.

**진행 조건:** 각 자식 설정의 관측 수준과 부모의 최종 완료가 확인돼야 한다. worker 토큰만 줄고 부모 통합 비용이 증가한 결과를 전체 절감으로 표시하지 않는다.

## E07

### 관찰·정책 보정·환경 변화

**가설:** 기록을 활용한 점진적 정책 변경이 새 작업군에서 회귀를 줄일 수 있다.

- 고정 프로필의 실제 실행과 Decisions의 추천만 기록하는 shadow 단계를 분리한다. 추천을 실행한 것처럼 집계하지 않는다.
- 같은 저장 신호에 정책을 재생해 선택 차이를 확인한다. 새로운 질문·입력·분류 모델이 필요한 정책은 별도 분류 자료가 필요하다.
- 균형 잡힌 비교 실행 자료로 작업군별 보정을 검토한다. 선택된 경로의 로그만으로 다른 경로의 성과를 추정하지 않는다.
- 실행기·모델·프로필·hook 변경 시 이전 capability 검증의 유효성을 확인하고, 이전 정책으로의 복귀는 새 실행부터 적용한다.
- 온라인 학습이나 off-policy 추정을 도입하려면 실제 배정 확률과 비교 지원 범위가 먼저 확보돼야 한다. MVP에서는 도입하지 않는다.

**진행 조건:** 선택 차이와 실제 성능 근거가 구분되고, 새 저장소·새 과제군에서 보정의 이득을 독립적으로 확인해야 한다. 잠금 평가를 반복해서 튜닝에 사용하지 않는다.

## E08

### 로컬·클라우드 실행의 후속 비교

**가설:** 허용된 데이터 처리 범위와 실제 장치 상태를 고려하면 유용한 로컬·클라우드 배정이 가능하다.

- 먼저 local-only 요청의 원격 분류·로그 전송이 0회인지 확인한다. 원격 Decisions를 사용한 실행은 원격 처리로 분류한다.
- 실행기별 입력·도구·컨텍스트·thinking 제어·출력 한도 지원을 확인한다. 같은 effort 문자열을 동일한 계산량으로 비교하지 않는다.
- cold/warm 적재, 모델 교체, 동시 실행에 따른 장치 자원 경쟁을 분리해 측정한다.
- 돈·시간·에너지·장치 점유 중 실제 측정한 항목만 보고하고, 로컬 실행 비용을 자동으로 0으로 두지 않는다.

**진행 조건:** 기본 Codex 경로의 가치가 먼저 확인돼야 한다. 사용할 로컬 실행기와 모델은 이 문서에서 고정하지 않으며, 기능·품질·데이터 조건을 충족하는 경우에만 후보로 추가한다.

## 관련 연구와 설계에 반영한 점

아래 자료는 직접 확인한 1차 연구다. 기존 연구가 보여준 사실과 본 프로젝트에 적용하는 추론을 구분한다. 논문의 비용 절감률을 AI Decisions의 성능 목표나 예상 결과로 옮기지 않는다.

| 자료 | 연구에서 확인한 내용 | 우리 설계에 대한 추론 |
| --- | --- | --- |
| [RouteLLM: Learning to Route LLMs with Preference Data](https://arxiv.org/html/2406.18665v4) | 응답 선호를 활용해 모델을 선택하고 무작위 라우터와 비교. 학습 데이터와 평가 영역의 차이를 분석 | 대화 선호가 저장소 수정의 성공을 대신하지 않으므로 작업군별 평가와 비율을 맞춘 기준이 필요 |
| [RouterBench: A Benchmark for Multi-LLM Routing System](https://arxiv.org/html/2403.12031v2) | 여러 모델의 결과와 사후 최선 선택을 비교. cascade 평가에서는 judge 오류를 주입해 민감도를 분석 | 먼저 후보 결과로 개선 여지를 살피고, 검증기 오류가 완료 품질에 미치는 영향을 평가 |

코딩 에이전트는 긴 맥락, 도구 사용, 파일 변경, 중단·복구, 결과 통합을 포함하므로 이 자료들의 결과를 그대로 일반화하지 않는다. 이 프로젝트의 후보 기여는 모델과 effort 선택을 분리해 평가하고, 실제 설정의 관측 수준과 검증된 완료 비용을 연결하는 데 있다. 신규성·우월성은 아직 검증되지 않았다.

## 보고서 형식

실험 보고서는 다음 정보를 포함한다.

- 데이터·저장소·정책·질문·프로필·실행기·검증기 버전과 시작 상태.
- 비교 대상·주 지표·품질 허용 기준·시간 한도·실제 실행 건수.
- 선택·요청·관측 설정, 실패·미관측·중단·지원 불가 처리.
- 과제군별 완료율·완료당 비용·실제 지연·제한 완료시간과 불확실성.
- 원시 사용량, 가격 출처, 추정·미정산 항목, 실행하지 않은 비교.
- 회귀 사례, 검증기의 오판, 다음 변경의 근거와 보류할 아이디어.

보고서는 모든 방식의 원시 실패를 포함한다. 구현하지 않은 기능, 실행하지 않은 검사, 아직 추정에 불과한 반사실 결과를 완료된 사실로 표시하지 않는다.
